# BRANCHING · 分支模型与合并门禁

> 用户要求原话：
> **「当前项目需要一个主分支 master，然后开发/冒烟测试/新功能等这些分支你们团队可以自己根据实际创建，但有一点需要注意：未通过实际测试的开发结果严禁合入 master。」**
>
> **适用范围**：本纪律对**四个仓库的 `master` 均适用**。下文以 **RoboMind-S3** 为具体执行对象；其余仓库照搬，把「RoboMind-S3」换成本仓即可，A–E 组的具体判据按各仓实际调整（VVOS 用构建 + ctest，RoboMind 用构建 + 烧录 + 串口）。
>
> **版本状态不写在这里** —— 各仓当前的 HEAD/分支/远程可达性见 [`PROJECTS.md`](PROJECTS.md) §5，那里配了自证命令，跑一次就知道有没有过期。
>
> **为什么这份文档的重点在第 3 节**：本项目从开始到现在反复撞的都是"看起来验证了、实际没验证"——测试没跑、代码没执行、解码通过但零吞吐、符号不在但代码在、静态池被裁掉。**合并是人最后一次能拦住它们的地方**；如果这里也只靠"我记得测过了"，那前面所有的判据规范都白写。

---

## 1. 分支模型

| 分支 | 职责 | 生命周期 | 允许直接提交 |
|---|---|---|---|
| **`master`** | **唯一可发布分支**。任何时刻它都必须能构建、能烧录、行为已验证 | 永久 | ❌ **禁止**（只接受合并，见 §2） |
| `feat/<slug>` | 新功能。可长期存在、可半成品 | 合入后删 | ✅ |
| `fix/<slug>` | 缺陷修复。**必须写清修的是什么现象** | 合入后删 | ✅ |
| `smoke/<slug>` | **只做验证不改产品行为**的临时分支（探针、测量、对照组） | 用完即删 | ✅ |
| `docs/<slug>` | 文档、规格、勘误 | 合入后删 | ✅ |
| `exp/<slug>` | 不保证能用的探索（**永不合并**，结论以文档形式回 master） | 删或不删 | ✅ |

### 命名规范

```
<type>/<kebab-slug>            feat/ppm-producer-startup
                               fix/export-metrics-staleness
                               smoke/console-uart-vs-jtag
                               docs/branching-policy
```

- 全小写、连字符分隔、不超过 40 字符；
- **`<slug>` 要能被人读懂**：`feat/thing` 不合格，`feat/wire-codec-11fields` 合格；
- 禁止 `master` / `main` / `dev` / `tmp` / 个人名作为长期分支——**多一条长期分支就多一条需要判断"它现在是什么状态"的分支**。

### 为什么没有 `develop`

本项目的现实是**单人 + 多 Agent 并行**，不是团队流水线。加一条 `develop` 只会让"master 落后一个整合步骤"，而那个步骤没人负责验证——**等于把门禁挪到一个更少人看的位置**。分支要少，门禁要硬。

## 2. 谁能合 `master`

| 决策点 | 谁 | 说明 |
|---|---|---|
| 是否合入 | **主理人决定 + 用户授权**（现状） | 这是当前现实，不是理想设计 |
| 执行合并 | 主理人或被明确授权者 | — |
| **是否能否决** | **任何人**（提出"证据缺失"即可暂停） | 门禁不是投票，是**证据检查**：谁指出某条判据没有证据，合并就暂停，直到补齐 |

**一条硬规矩**：**合并者必须是"看了证据的人"，不能是"被告知通过了的人"。** 如果合并者自己没打开过那份日志/那个构建输出，那这次合并**在流程上就是无证据合并**——即使工程确实通过。

## 3. 合并前置条件（本文档的核心）

### 3.0 通则：**能编译期拦的，不要留到门禁**

> **门禁依赖"有人记得跑"。编译期依赖"不满足就编不过"——后者没有"忘了跑"这个状态。**

这条不是理论，是本项目**已经吃过两次亏**换来的：

| 事件 | 检查长什么样 | 为什么无效 |
|---|---|---|
| 夹具隔离 | `nm <elf> \| grep build_mock_frame` | **恒通过**——匿名命名空间 + `-Os` 内联后**符号根本不存在**，两种配置都查不到 |
| 静态段检查 | `grep '\.bss'` 看 map | **误判 `0x0`**——只匹配到空段，漏了带符号名的那几行 |

**两次都是"检查存在但无效"**：检查写了、也跑了、还通过了——但通过的原因不是"没问题"，而是**"这个检查看不见问题"**。

**编译期闸门不会犯这个错**：它只有"编过"和"编不过"两种状态，**没有"跑没跑"这个中间态**。

| 适用 | 不适用 |
|---|---|
| 配置值必须满足某条件（如某 `CONFIG_*` 字符串必须含某约束） | **需要真机行为才能判断的**（如"默认态零影响"只能靠串口日志） |
| 某宏必须与某功能互斥（如 `MOCK_FIXTURE && NDEBUG` ⇒ `#error`） | 涉及运行期时序的（如"判死延迟 ≤ 4 s"） |
| 某结构体尺寸/布局必须固定（`static_assert(sizeof == 24)`） | 需要人眼判断的（如"好不好看"） |
| 两个类型必须一致（防止两份定义） | — |

**一个已落地的样板**（工程师本轮补的）：构建期 `static_assert` 检查 `CONFIG_ROBOMIND_AI_SYSTEM_PROMPT` 必须含 `English` 约束，并做了**双向验证**（中文提示词 ⇒ 编译失败；英文 ⇒ 通过）。

> **双向验证是这条通则的必要条件**：一个"永真"的 `static_assert` 也是"检查存在但无效"。**只验通过方向不够，必须验失败方向**——这和 §3.2 的负向用例是同一件事。

### 3.1 使用方式

1. 每个 PR（或合并请求）**在描述里逐条粘贴证据**，不是"已测试"三个字；
2. 合并者**逐条核对证据本身**（不是核对"有没有写证据"）；
3. **任何一条没有证据 = 不通过**。没有"这条我觉得没问题"这种档位。

### 3.2 清单

#### A 组 · 构建与烧录（基础，缺一不可）

> **例外**：若本次改动集**完全不含代码路径**（判定方式见 §3.4），可只做 **A1**，A2–A4 豁免。**技术改动一律全检。**

| # | 判据 | 证据形式 | 失败处置 |
|---|---|---|---|
| A1 | 构建通过 | `idf.py build` **退出码 0** + 最后一行 `Project build complete` | 停在本地 |
| A2 | **烧的就是编的** | 串口启动日志里的 `compile time <date> <time>` **与本次构建时间一致**；或 `idf.py flash` 输出的 `Hash of data verified` | 重烧 |
| A3 | 烧录无跳过 | flash 输出含 `Wrote <N> bytes` 且 `Hash of data verified` | 重烧并查串口占用 |
| A4 | 启动无崩溃 | 启动后 10 秒内**无** `Guru Meditation` / `abort()` / `Backtrace` / `rst:0x...` 异常复位 | 停止合并 |

> **A2 为什么单列**：本项目真实踩过"板子上跑的不是这份源码"的风险（早期 ELF 与日志不同源）。**只看"烧录成功"不能证明烧的是新固件。**

#### B 组 · 默认态零影响（**仅针对特性开关类改动**）

> 适用条件：改动引入了 `CONFIG_*` 开关且**默认关闭**（如 `ROBOMIND_PPM_PRODUCER_ENABLED`、`ROBOMIND_PPM_MOCK_FIXTURE`）。

| # | 判据 | 证据形式 | 失败处置 |
|---|---|---|---|
| B1 | 默认构建设施没有被激活 | 串口**无**该特性的新增日志行（如 `[producer]` / `[wire]` / `[ppm ]` 各 **0 条**） | 停 |
| B2 | **开关本身是关的** | `grep -c 'CONFIG_XXX' build/config/sdkconfig.h` ⇒ **0** | 停 |
| B3 | 原有基线不退化 | `[mem]` 五点 × 四值（`free`/`largest`/`min_free`/`psram_free`）= **20 个数**与改动前**逐项相同** | 停 |
| B4 | 静态段未被悄悄改写 | `.dram0.bss` 与改动前**同值或在已知差异内**（见 D2 的口径） | 停 |

> **B2 的写法为什么是 grep 宏而不是查符号**：`nm` 查不到某个函数，**不等于**那段代码不在——它可能被内联/内联展开后连符号都没有。**查生成代码的输入（宏），不查产物（符号表）。**（本项目实测：夹具开启的构建里 `nm` 同样查不到 `build_mock_frame`。）

#### C 组 · 关键行为验证（**每条改动都要有自己的判据**）

| # | 判据 | 证据形式 |
|---|---|---|
| C1 | 改动声明的**主行为**成立 | 具体日志行 + 断言值。**必须写清"哪一行、什么值、为什么这个值"** |
| C2 | 边界/降级路径也跑过 | 至少一条负向或降级用例的日志 |
| C3 | 没有"零吞吐式通过" | 判据必须断言到**链路终点**，不是中间一环（例：只断言 `decode == OK` 不够，要断言帧真的进了路由 / 真的发出去了） |
| C4 | 计数器与采集窗口一致 | 若引用累积计数，说明**打印周期**与**采样窗口**的关系（本项目踩过：`[wire]=320` 而 `ok=300`，实际是统计行每 100 帧才打一次） |

#### D 组 · 静态资源与内存（防"偷偷加开销"）

| # | 判据 | 证据形式 |
|---|---|---|
| D1 | **必需项还在**（防链接时被裁） | `nm <elf> \| grep -c " T ppm_run"` = 1；`grep -c " D ppmi_ref_backend"` = 1。**删掉锚点会让 46,911 B 静态池静默消失而没有任何运行时异常** |
| D2 | **新增代码没有引入静态存储** | map 里新增 `.o` 对 `.dram0.bss` / `.dram0.data` 的贡献为 **`0x0`** |
| D3 | `.text` 变大**不算问题**（代码本来就会变大） | 记录即可，不参与判定 |
| D4 | 若有新的运行期分配 | 给出 `lv_mem_monitor` / `heap_caps` 的前后对比 |

> **D2 为什么不是"`.bss` 总数不变"**：含删除的重构必然让总数变（删一个含静态变量的文件就 −8 B）。**"总数不变"是字面不可达的判据**，且它会被"删 8 加 8"骗过。**分别盯"新增为零"和"必需项还在"，才抓得住真实意图。**

#### E 组 · 文档

| # | 判据 | 证据形式 |
|---|---|---|
| E1 | 若改了行为，文档已同步 | 列出改了哪个文件哪一节 |
| E2 | 若勘误了旧结论，**旧文保留**并标注原因 | 勘误表条目（新增行，不删旧行） |
| E3 | 未解决的边界写明了 | 该单的"不解决的问题"一节 |

### 3.3 四类判据的优先级（时间不够时先砍哪个）

**不可砍**：A 组、B2、C1、C3、D1、D2。
**可延后到下一次合并**：C2 的部分边界、D4、E3。
**永不砍**：**任何"必需项还在"的检查（D1）**——它挡的是"静默变好但实际变差"。

## 3.4 豁免：用**改动路径**判定，不用分支名

**问题**：纯文档改动烧一次板子没有意义。但豁免范围必须**可机械判定**——不能靠"我觉得这是文档改动"。

### 判定规则

> **豁免条件**：本次合并的改动集**完全不含**下列路径时，只需 **A1（构建通过）**，不需要 A2–A4（烧录/串口/行为验证）。
>
> ```
> main/   components/   platform/   CMakeLists.txt
> sdkconfig*   partitions.csv   tools/
> ```

```bash
# 判定方式：路径匹配，不依赖人工判断
BASE=$(git merge-base origin/master HEAD)
if git diff --name-only "$BASE"..HEAD | grep -qE '^(main/|components/|platform/|CMakeLists\.txt|sdkconfig|partitions\.csv|tools/)'; then
  echo "TOUCHED_CODE=1  ⇒ 全检（A+B+C+D+E）"
else
  echo "TOUCHED_CODE=0  ⇒ 豁免：只需 A1"
fi
```

### 为什么不用"分支名豁免"

| 方案 | 能否伪装 |
|---|---|
| 按分支名（`docs/*` 豁免） | ❌ **分支名可以随便起**。在 `docs/xxx` 上夹带 `main/` 的改动，照样豁免——**这是把一个判定交给了一个完全自由命名的字符串** |
| **按改动路径** | ✅ **路径无法伪装**：改了哪个文件就是哪个文件 |

**而且按路径判定有两个额外好处**：

1. **在 `feat/xxx` 上只改文档，也自动适用豁免**（不必为了拿豁免去改名分支）；
2. **在 `docs/xxx` 上夹带代码改动，会被强制全检**——**豁免跟随内容，不跟随意图声明**。

### 一条不动摇的边界

> **技术改动一律全检，无论它在哪个分支上、无论提交信息怎么写。**

**豁免只面向"改动集不含代码路径"这一种情况**，不面向任何其他理由（"改动很小"、"只改了一个常量"、"我本地测过了"都不构成豁免理由——那些走 §7 的 `BREAK-GLASS` 流程，**留下痕迹**）。

## 4. 可粘贴的门禁脚本（骨架）

> 目的不是自动判定通过，而是**自动收集证据**。判定仍需人看，但**收集不能靠人回忆**。

```bash
#!/usr/bin/env bash
# merge_precheck.sh <build_dir> <serial_log>
set -u
BD="${1:-build}"; LOG="${2:-}"
fail=0
chk() { printf '%-46s %s\n' "$1" "$2"; [ "$2" = "OK" ] || fail=1; }

# A1 构建产物存在且是本次的
[ -f "$BD/robo_mind_s3.bin" ] && chk "A1 app bin 存在" OK || chk "A1 app bin 存在" "FAIL"
echo -n "   bin 时间: "; stat -c '%y' "$BD/robo_mind_s3.bin" 2>/dev/null

# A2 同一性的唯一可信证据在串口日志里
if [ -n "$LOG" ]; then
  grep -m1 -o 'compile time .*' "$LOG" | sed 's/^/   /' || chk "A2 compile time 行" "FAIL"
  grep -c 'Hash of data verified' "$LOG" | sed 's/^/   Hash verified 次数: /'
  grep -cE 'Guru Meditation|abort\(\)|Backtrace' "$LOG" | sed 's/^/   A4 崩溃迹象: /'
else
  echo "   A2/A3/A4 需要串口日志（未提供 ⇒ 视为无证据）"; fail=1
fi

# B2 默认关闭的开关：查宏，不查符号
grep -c 'CONFIG_ROBOMIND_PPM_PRODUCER_ENABLED' "$BD/config/sdkconfig.h" 2>/dev/null \
  | sed 's/^/   B2 producer 开关命中(默认构建应为 0): /'
grep -c 'CONFIG_ROBOMIND_PPM_MOCK_FIXTURE' "$BD/config/sdkconfig.h" 2>/dev/null \
  | sed 's/^/   B2 夹具开关命中(默认构建应为 0): /'

# D1 必需项还在（防链接期静默裁掉）
grep -c ' T ppm_run$'          <(nm "$BD/robo_mind_s3.elf" 2>/dev/null) | sed 's/^/   D1 ppm_run(应=1): /'
grep -c ' D ppmi_ref_backend$' <(nm "$BD/robo_mind_s3.elf" 2>/dev/null) | sed 's/^/   D1 ppmi_ref_backend(应=1): /'

# D2 新增 TU 的静态段贡献（应为 0x0）
for o in ppm_producer wire_codec; do
  grep -E "${o}\.cpp\.obj" "$BD/robo_mind_s3.map" 2>/dev/null \
    | grep -E '^\s+\.(dram0\.bss|dram0\.data)' | sed "s/^/   D2 $o: /"
done
echo; [ $fail -eq 0 ] && echo "== 证据收集完成，请人工逐条核对 ==" || echo "== 有缺口，禁止合并 =="
exit $fail
```

**两个设计取舍要说明**：

| 取舍 | 理由 |
|---|---|
| 脚本**只收集、不判定通过** | 自动判"通过"会把人的责任转移给脚本；而脚本无法判断"C1 这个值对不对" |
| 缺串口日志 ⇒ **直接判缺失** | 本项目所有"看起来验证了"的事故，缺的都是**运行时证据**。宁可不合并，不要无证据合并 |

## 5. 回滚策略

| 情况 | 做法 | 理由 |
|---|---|---|
| 已合入 master 且**尚未 push** | `git revert` 或 `git reset --hard` 均可 | 无外部影响 |
| 已合入且**已 push** | **只允许 `git revert`**（新增一个反向提交） | `reset` 会改写已发布历史；下游 fork/缓存可能仍留住旧提交（本项目早前处理 SSID 泄漏时已确认过这一点） |
| 已烧录发现问题 | 先 `git revert` → 重新构建 → 重烧，**不要"在 master 上直接改"** | 直接改会让"master 曾经是坏的"这段历史消失，下次同样的坑会重犯 |
| 合错但**当天发现** | 仍需 revert 记录，不例外 | **revert 记录本身就是"这条判据漏了什么"的证据**；删掉它等于删掉唯一的复盘材料 |

**禁止**：`git push --force` 到 master；在 master 上直接 `commit --amend` 已 push 的提交；用"重新建一个干净的 master"来解决历史问题。

## 6. 为什么这份门禁长这样（与判据设计规范的映射）

本文的每条判据都对应 `three-way-integration-2026-11-13.md` §9 已总结的一种失效：

| §9 的形态 | 门禁里对应的防线 |
|---|---|
| 假绿灯①：测试从未执行 | A1 要求**退出码 + 完成行**，不接受"应该没问题" |
| 假绿灯②：代码从未执行 | B1/C3 要求断言到**运行痕迹**与**链路终点** |
| 假绿灯③：解码通过但零吞吐 | C3「必须断言链路终点」 |
| 假绿灯④：符号不在但代码在 | B2「查宏不查符号」 |
| 假绿灯④：必需项被静默裁掉 | **D1**（最隐蔽的一种——连运行时都没有异常） |
| 假绿灯⑤：技术指标全绿但目标未验证 | **本文 §8「不解决的问题」+ 交付时必须声明"证明了什么/没证明什么"**（例：A–E 证明能跑、不越界、对比度达标，**不证明好看**） |
| **假绿灯⑥：检查存在但无效** | **§3.0 通则**——能编译期拦的不留到门禁；且**编译期闸门必须双向验证**（只验通过方向不够，一个永真的 `static_assert` 也是无效检查） |
| 规则 3：判据要能机械执行 | 全表要求"证据形式"，不接受"已测试" |
| 规则 6：陈旧/间接观测 | A2「compile time 对齐」；B2「查宏不查符号」 |
| 规则 5：划出未证边界 | E3；以及 C4「计数器周期 ≠ 采集窗口」 |

## 7. 破例流程（允许，但必须留痕）

**没有破例流程的规矩会被绕过，而且绕过之后没人知道。** 所以给一条明路：

| 步骤 | 要求 |
|---|---|
| 1 | 在 PR 描述里显式写 `BREAK-GLASS: <哪条判据>` |
| 2 | 写明**为什么现在必须破**（例：硬件不在手边、阻塞用户演示） |
| 3 | 写明**补证的计划与时间点** |
| 4 | 合并者在合并提交信息里带上这句 `BREAK-GLASS` —— 它会被 `git log --grep=BREAK-GLASS` 一次性捞出来 |

**破例不是失败，隐瞒才是。** 一份能列出所有破例记录的 `git log`，比一份"从不破例"的自我叙述可信得多。

## 8. 不解决的问题（边界）

| 未解决 | 说明 |
|---|---|
| 门禁无法自动判断"C1 这个值对不对" | 仍需人看证据；本文只保证"证据被收集、缺口被发现" |
